# 시나리오 다중 루트 — 1단계 현황 조사 · 설계안 (2026-10-23)

> 사용자 요청 원문(2026-10-23): *"같은 시나리오에서도 여러 개의 루트가 존재하고 해당 부분이 랜덤으로 하나가 정해져서, 같은 시나리오, 같은 난이도를 하더라도, 사용자가 다른 경험을 할 수 있게 … 지금 시나리오 전체를 대상으로 해보자"*
> 브랜치 `claude/scenario-multi-route-7bbbc5` = main `239a417`. **1단계 산출물 — 코드 변경 0 · 실 키 호출 0.** 2단계(구현)는 메인 세션이 사용자 승인을 받아 지시한다.

## 0. 금지 · 범위 (먼저)
- 근거(공개 자료) 없는 루트는 만들지 않는다. 2절 표에 출처가 없는 루트는 설계안에 넣지 않았다.
- 실제 범행에 그대로 쓸 수 있는 세부(만날 장소 · 시간 · 실존 앱명 · 실제 계좌 · 숙박업소 격리 지시)는 루트에 넣지 않는다 — 기존 안전 규칙(AC-102 · D-104 · §115.2 "숙박업소 격리는 통화 범위 밖")을 그대로 따른다.
- 이 문서의 수치 중 "추정"으로 표시한 것은 실측이 아니다. 확인 방법을 같이 적었다.

## 3. 설계안

### 3.1 루트 정의 구조 — 새 타입을 만들지 않고 **흐름 변형을 루트로 쓴다**
루트 1개 = (시나리오 × 난이도)마다 흐름 변형 1개. 같은 결말을 가진 난이도별 변형은 **루트 키**로 묶는다.

| 필드 | 지금 | 추가 · 변경 | 쓰는 곳 |
|---|---|---|---|
| `variantId` (`fv-xxxx`) | 있음 | 그대로 — 새 루트는 새 ID. ⛔ 기존 ID 재사용 · 삭제 금지 | 세션 문서 |
| `routeKey` | 없음 | **추가(서버 전용)** — 시나리오 안에서 결말 이름, 예 `transfer` · `cash-handoff` · `gold` · `voucher` · `app-remote` · `loan-exec`. 난이도가 달라도 같은 결말이면 같은 키 | 배정(최근 회피) · 리포트 표시 · 테스트 |
| `routeLabel` | 없음 | **추가** — 리포트에 보일 한 줄 이름(예: "현금 전달형"). D-3 결정 시에만 서버 밖으로 나간다 | 리포트 |
| `stages[]` | 있음 | 그대로. 루트마다 **첫 1~2단계(시나리오 진입부)는 같게**, 결말 단계만 다르게 쓴다(공개 카드 문구 C3 "첫 마디" 일치 유지) | 프롬프트 흐름 블록 |
| `sms[]` · 모의 화면 | 있음 | 루트가 쓰는 문자만 선언. 새 화면은 기존 `credential-form` · `app-install` 종류만 재사용(새 kind 0 목표) | 문자 게이트 · 백스톱 · 도달 판정 |
| `goalFollowUpUserTurns` | 있음(2벌) | 결말 뒤 말로 하는 후속이 있는 루트만 | 끊기 C-5 |

| 기본 페르소나(`*.prompt.ts`) | 결말 방식이 박혀 있음(예: 기관 사칭 "안전계좌" 3회 · 손주 "상품권" 5회 — `grep` 집계) | **공통부(인물 · 진입 · 말투)와 결말부를 나눈다** — 결말은 변형의 단계 · 수법으로만 들어가게. 안 나누면 페르소나와 흐름 블록이 서로 다른 결말을 지시한다 | 모든 시나리오 프롬프트 |

**끊기 판정 매핑(확인 무력화 고급 7종 — 기관 · 카드사 · 대출 · 환급 · 택배 · 은행 · 카드 배송, `verifyIntercept.ts:106-178`):**
| 루트의 결말 종류 | 4행 "할 일 완료" | 불변식(테스트로 고정) |
|---|---|---|
| 문자 링크 화면 제출(이체 · 신청 · 사이트) | C-1 (뒤에 말 단계가 있으면 C-5) | 결말 문자는 `required: true` |
| 앱 설치 응낙 | C-2 | 설치 문자 `required: true` |
| 계좌 문자만 | C-3 | 필수 문자 ≥ 1 |
| 말로만 끝나는 결말(현금 · 금 전달 약속 · 상품권 핀 · 대출 동의) | C-4 (문자 선언 0 ∧ 발화 ≥ 8) **또는** 새 행 | ⚠️ 문자 선언이 있는데 필수 0이면 4행이 영영 안 열린다(`goalAction.ts:63`) — "선언 ≠ 0 ∧ 필수 = 0" 조합 금지 |

**리포트 판정 매핑:** 리포트는 변형 수법 라벨로 해석하고(`generateReportCore.ts:113`) 화면 하나에서 가장 깊은 단계 1건을 고른다(`smsTimeline.ts:224` 표 1~6행). 루트가 기존 화면 종류만 쓰면 판정표는 그대로다. 말로 끝나는 결말은 대화 분석이 "요구 수법"(payment_demand 등)으로 분류해야 하므로 새 라벨은 분류 테스트(`flowVariants.test.ts:326` "other로 떨어지지 않는다")를 통과해야 한다.

### 3.2 무작위 배정 규칙
| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| A 현행 회전 | 직전 다음 순번(A→B→C→A) | 변경 0 | **무작위가 아니다** — 순서가 외워진다 |
| B 무작위 + 직전 회피 | 직전 루트를 뺀 나머지에서 균등 무작위 | 단순 · 연속 0 | 3개 이상이면 한 루트를 오래 못 볼 수 있다 |
| **C 섞은 덱(권장)** | 루트를 섞어 덱을 만들고 하나씩 꺼낸다. 덱이 비면 다시 섞되 새 덱 첫 장 ≠ 직전 | 무작위 + **모든 루트를 한 번씩 본 뒤에야 반복** + 연속 0 | 회전 문서에 남은 덱 배열 저장(필드 1개) |

공통: 세션 시작 때 1개 확정 → 세션 문서 `flowVariantId`에 기록 → 세션 동안 고정(이어하기 · 재연결 · 리포트 모두 같은 값 — 현행 그대로). 저장은 지금의 `users/{uid}/variantRotation/{시나리오}__{난이도}` 문서 1건 키 조회 · 트랜잭션 확정을 그대로 쓴다(새 인덱스 0 · 클라 쓰기 거부 유지 · `variantAssignment.ts` 머리 금지 X6). 난수는 서버 `crypto.randomInt`, 테스트는 난수 주입.
덱의 범위(난이도별 vs 시나리오 전체)는 결정 D-2.

### 3.3 난이도와 루트의 관계 — 권장: **루트 = 결말 방식, 난이도 = 깊이 · 압박**(두 축을 분리)
| 난이도 | 루트 수(목표) | 같은 루트의 모양 |
|---|---|---|
| 초급 | 2 (근거 있는 결말 중 1~2단계로 끝나는 것) | 진입 → 곧바로 결말 요구(현행 초급 규칙 AC-096 (d) — 이탈 차단 D2~D6 0) |
| 중급 | 2~3 | + 본인 확인 · 인증번호 · 링크 1개 |
| 고급 | 3 | + 확인 무력화 · 후속 단계 · 화면 다단계 |
| 고급 전용 3종 | 3 | 고급만 |

⚠️ 초급 사전 브리핑은 "초급 변형 전부의 수법 교집합"이라(`flowVariants.ts:1422`) 루트가 늘면 **결말 수법이 브리핑에서 빠진다** → 결정 D-4.

### 3.4 리포트 · 되짚어보기 표시 — 결정 D-3

### 3.5 챌린지(지인 보내기) — 권장: **적용**
받는 사람은 지금처럼 `hash(challengeId) mod 루트 수`로 정한다(보낸 사람도 모른다 · 회전 문서 0 · 익명 쓰기 최소 §69 유지). 단 풀 필터는 그대로: 고급 통화 중 설치 문자(Q2) 루트는 챌린지에서 빠진다(`variantPool.ts:7-20`). ⇒ 카드사 · 대출 고급은 챌린지용 비설치 루트가 1개 이상 있어야 하고, 카드 배송은 지금 챌린지 풀 0(챌린지 불가 — 현행 유지).
⚠️ 메신저 중 통화로 넘어가는 시나리오(자녀 사칭 · 정부지원금)는 챌린지 생성 자체가 거부된다(`challenge/index.ts:111-118` `escalation_not_supported`). 메신저 챌린지 적용 대상은 지인 사칭 · 택배 문자 2종뿐이다.

|---|---|---|
| 보이스톡 발신 화면 | 통화가 "사기범이 건다"뿐 아니라 "참가자가 걸게 시킨다"("이 번호로 보이스톡 해 줘")일 수 있다 | 통화 단계에 시작 주체(`callInitiator: scammer \| participant`)를 루트 값으로 둘 자리. 지금 값 = scammer |

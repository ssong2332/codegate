- 관계: **ADR-0001~0010 중 어느 것도 뒤집지 않는다.** ADR-0004(프롬프트 서버 소유·인젝션 방어)·ADR-0007(문자 전달 모델)·ADR-0009(확인 무력화 순간 주석)와 접점이 있으나 전부 **무개정 재사용**이다. ⚠️ **ADR이 아닌 인계 1건은 명시적으로 뒤집는다** — Architecture.md **§15.10.8**의 *"`SCENARIO_AXES[scenarioId].exitBlock`이 L3의 입력이다"*. §15.10.8 자신이 *"어느 옵션이든 T81이 확정하고 근거를 남길 것 — 이 절은 권고이지 확정이 아니다"* 로 T81에 위임한 범위 안이다.

## Context

사용자 지적(2026-07-25): *"시나리오 고급이어도 전형적인 보이스 피싱 수법이라고 느껴져."* planner는 직접 원인을 이렇게 판정했다 — 현행 난이도는 **압박 강도·수법 노출도·지속성만** 조절하고 **축 D(이탈 차단)를 건드리지 않는다.** 그래서 난이도를 **4개 레버**로 재정의했다(AC-074): L1 수법 노출도 · L2 압박 지속성 · **L3 이탈 차단 깊이** · **L4 요구 도달 단계성**.

이 ADR이 풀어야 하는 힘은 넷이다.

1. **L3만 시나리오별로 갈린다.** L1·L2·L4는 시나리오와 무관한 규칙이라 현행 공통 블록(`DIFFICULTY_MODIFIERS`, `promptAssembly.ts:105-118`)에 그대로 들어간다. 그러나 L3는 (i) D3 재현에 **메커닉**(T83의 모의 재연결)이 필요하고 (ii) D4 절차 정당화는 **페르소나 적합성**에 갈린다(가족 사칭이 접수번호를 부르지 않는다). 문자열 하나로 두 갈래를 표현할 수 없다.
2. **13종×3단계 = 39벌 저작은 이미 기각돼 있다**(§15.3.1). 유지비뿐 아니라 *한 벌만 고쳐 안전 문구가 빠지는* 드리프트 위험을 3배로 만든다. 그 판정은 유효하며 이 ADR이 뒤집지 않는다.
3. **⚠️ T81의 유일한 입력으로 지목됐던 축 표가 콘텐츠보다 좁다.** §15.10.8은 `SCENARIO_AXES[].exitBlock`을 L3의 입력으로 인계했는데, T82 reviewer가 `"전화 끊음 저지"`(D5) 보유 9종 대비 태깅 4종의 언더카운트를 정량화했고, **직접 전수 대조한 결과 오차는 D5 5행이 아니라 D1·D2·D5에 걸친 9/13행**이었다(§17.1.1). `axes.ts:154-164` 주석이 이미 *"이 표는 시나리오의 **주된** 좌표를 적은 것이지 콘텐츠의 모든 수법을 망라한 것이 아니다"* 라고 자인한다.
4. **AC-065는 불변이다.** 난이도는 어떤 안전장치도 게이팅·약화·우회하지 않으며, 무해화 경계는 고급에서도 동일하다. *"고급 = 더 진짜 같은 압박"이지 "고급 = 더 진짜에 가까운 위험 정보"가 아니다.* 이 불변식은 문구가 아니라 **조립 순서**(§15.5, 가드레일이 언제나 마지막)와 T83이 추가한 자동 테스트 2건으로 이미 고정돼 있다.

## Decision

**(A) L3는 `SCENARIO_AXES`를 읽지 않는다. (B) 조립은 공통 블록 유지 + L3 변형 2벌(총 4벌) + 옵션 1비트로 한다. (C) 세 난이도의 축 D 규칙은 비대칭이다 — 초급은 상한, 중급은 무강제, 고급은 하한.**

### (A) 왜 축 표를 읽지 않는가

| Option | Pros | Cons |
|---|---|---|
| **축 표를 읽지 않는 판정 규칙(채택) ✅** | **재발 방지가 되는 유일한 안** — §15.10.4가 이미 *"게이트는 값을 **가졌다**는 사실만 증명하고 값이 **맞다**는 것은 증명하지 못한다"* 고 자인했다 · §15.10.3이 정한 축 표의 소비처(테스트 단언 + 리포트 스크립트 **2곳**)를 지킨다 · 커버리지 목적의 좌표 수정이 **라이브 프롬프트를 조용히 바꾸는 일이 없다** · 실제로 L3가 표를 **필요로 하지 않는다**(초급=상한, 고급=하한이라 "시나리오가 무엇을 가졌는지" 알 필요가 없다) | 축 표와 난이도 사이에 자동 연결이 없어, 신규 축 값이 생겨도 난이도가 저절로 따라가지 않는다 — `L3_DEPTH_TABLE`의 키 `deepEqual` 게이트가 **신규 시나리오는** 강제하지만 **신규 축 값은** 강제하지 않는다(정직 고지) |
| 표를 T85에서 정정하고 그대로 소비(안 a) | 좌표와 프롬프트가 한 번은 정확히 맞는다 | **9행 전면 재검토가 T85 diff에 섞여** T87 (1)의 "재구성 전 고급 vs 후 고급" 대조가 두 변인을 동시에 움직인 비교가 된다(AC-074 증거 오염) · `axes.ts`를 T95가 동시 편집 중 · 결합 자체는 그대로 남아 다음 언더카운트에서 같은 사고 재발 |
| 표 정정을 선행 태스크로 분리(안 c) | 증거 오염 없음 · 커버리지도 정확해짐 | 사용자 지적의 **직접 해소(T85)가 커버리지 정확도 작업 뒤로 밀린다**(우선순위 역전) · 결합은 그대로 남는다 · 이 ADR이 표를 안 읽기로 한 이상 **선행일 이유가 사라진다** |

**안전 방향 논증(이 판정의 핵심).** 표의 오류는 **전부 누락(under-tagging)이며 허위 추가(over-tagging)는 0건**이다 — 태깅된 값은 모두 콘텐츠 근거를 갖는다(§17.1.1 대조표). 따라서 위험한 규칙은 정확히 하나, **"D가 몇 개인가"를 세는 규칙**이다(누락 = 과소 계수 → `tax-refund-scam`이 실제 D2+D5인데 1개로 읽혀 "초급 = 0~1개" 경계에서 오분류). 이 설계는 그 규칙을 **제거**한다. 반대로 "무엇을 부여할까"는 애초에 표를 볼 필요가 없다.

**표 정정을 포기하는 것은 아니다.** §17.11 **G60**으로 등재하고 소관을 축 모델 계열(T78/T82 후속)로 명시한다 — `courier-customs-scam`이 `D0_none`으로 보고되는 것은 사실과 다르며 **AC-076 커버리지 산출의 정확도 문제로 남는다.** 다만 그것은 난이도 태스크의 착수 차단 요인이 아니다.

### (B) 조립 모델

**`DIFFICULTY_MODIFIERS: Record<DifficultyLevel, string | null>` → `buildDifficultyBlock(level, opts): string | null`.** 블록 슬롯은 **4개**이고 실제 저작은 **3벌**이다(축소형은 빈 블록).

| # | 블록 | 조건 | 담는 레버 |
|---|---|---|---|
| 1 | `BEGINNER_BLOCK` | `beginner` | L1 + L2 + **L3 상한** + L4(1단) |
| — | *(없음, `null`)* | `intermediate` | **기준선 — 블록 미출력** |
| 2 | `ADVANCED_BASE` | `advanced` | L1 + L2 + **L4(2단)** |
| 3 | `ADVANCED_L3_PROCEDURAL` | `advanced` && `l3Procedural` | **L3 = D4 절차·서류 정당화** |
| 4 | `ADVANCED_L3_REDUCED` = **빈 블록** | `advanced` && !`l3Procedural` | — |

- **39벌 기각은 유지된다.** 4벌은 §15.3.1의 논증에 저촉되지 않는다 — 안전 문구(`SCENARIO_PROGRESSION`의 *"페이로드는 가상값만"*, `guardrailPreamble`)는 **여전히 시나리오·난이도 무관 단일 소스**이고 이 4벌 어디에도 복제되지 않는다.
- **D3는 이 4벌에 없다.** D3의 프롬프트 층은 T83이 만든 `VERIFY_INTERCEPT_RULE`이고 게이트도 `hasVerifyIntercept(id) && advanced`로 **이미 배선돼 있다**(`roleplay/index.ts:180`, `realtime/geminiProvider.ts:76-77`). **신규 게이트 0건.**
- **결합 수단 = `l3Procedural?: boolean` 옵션 1개.** `inCallSmsEnabled`/`verifyInterceptEnabled`와 같은 형태라 새 관례가 0개이고, `promptAssembly.ts`가 **타입 외 import 0**인 순수 문자열 조립 함수라는 성질이 보존된다. 모드 결정은 신규 순수 모듈 `functions/src/roleplay/l3Depth.ts`가 단독으로 하며 **`axes.ts`를 import하지 않는다**(D-46 정합 — 축이 프롬프트 경로에도 들어가지 않는다).
- **조립 순서는 바뀌지 않는다**(§15.5 확정 순서 1~8). 6번 항목이 내보내는 문자열만 길어지므로 T83이 추가한 `[T83 전수]` 2건과 `intermediate ≡ 기준선` 1건이 **무개정 통과**한다. L3 변형이 `difficultyLevel`이 아니라 `scenarioId`로 결정되므로 시나리오 전수 순회 테스트가 **자동으로 두 변형을 모두 훑는다** — 조합 축이 늘지 않는다.

### (C) 세 난이도 사전 정의값 — 비대칭 규칙

| | 초급 | 중급 | 고급 |
|---|---|---|---|
| 규칙 성격 | **상한(능력 제거)** | **강제 없음** | **하한(능력 추가)** |
| 허용 D축 값 | `{ D1_time_pressure }` | 콘텐츠가 가진 값 그대로 | 기준선 + **D4 필수** + **D3**(메커닉 보유 시 필수) |
| 동시 D 수법 상한 | **1개**(0 허용) | 없음 | 없음 |
| 요구 단계 수 | **1** | **1** | **2**(선행 1 → 최종 1, 3단 이상 금지) |

**이 비대칭이 AC-065를 구조로 보증하는 두 번째 장치다** — 난이도 블록은 **안전장치를 빼는 방향으로 절대 동작하지 않는다**(첫 번째 장치는 조립 순서).

- **중급을 강제하지 않는 이유:** PRD 표의 중급 값 `{D1,D2,D5}`를 강제하면 중급이 블록을 내보내야 해 §15.3.1의 기준선 불변식과 기존 테스트(`promptAssembly.test.ts:300-308`)가 동시에 깨지고, `kidnapping-threat`의 `D6`처럼 **중급이 기존 시나리오의 수법을 빼앗는다.** PRD 중급 행은 *현행 라이브러리 기준선에 대한 서술*이지 강제 대상이 아니다.
- **초급을 라벨 열거로 쓰지 않는 이유:** 같은 수법이 시나리오마다 6가지로 표기된다(`"확인 절차 차단"`/`"확인 차단"`/`"확인 전화 차단 유도"`/`"원격 확인 차단"`/`"주변 확인 차단"`/`"확인 차단 지시"` — §15.4.2 실측). 열거하면 표기가 다른 시나리오에서 조용히 빠져 **난이도가 시나리오마다 다른 뜻**이 된다. 따라서 **행동 범주로 서술**한다.
- **초급 상한은 이탈 차단 계열에만 적용된다.** 요구 계열은 초급에서도 그대로 일어난다 — `SCENARIO_PROGRESSION`의 *"반드시 구체적인 요구에 도달한다"* 는 세 난이도에서 불변이다.

### (D) L3 깊이 모드 — 판정 질문 1개

**`hasVerifyIntercept(id)` → `d3_and_d4` / `L3_DEPTH_TABLE[id]==="procedural"` → `d4_only` / 그 외 → `reduced`.**
`L3_DEPTH_TABLE`의 유일한 판정 질문은 **"이 페르소나가 접수번호·처리 단계·기한·담당 부서를 말해도 캐릭터가 무너지지 않는가"** 이며, 콘텐츠의 수법 수를 세지 않는다. 분포는 **5 / 4 / 4**(전체 13종, §17.5 표) — 기관·금융·서비스·협박 사칭 9종이 D4를 받고, **가족·지인 사칭 4종이 `reduced`** 다.

**⚠️ 이 표는 처방(prescription)이지 서술(description)이 아니다.** `SCENARIO_AXES`처럼 *콘텐츠보다 좁을* 수는 없지만, 각 행의 페르소나 적합성 판단이 맞다는 것은 여전히 사람의 판단이며 라이브 대조(T87 (1)·(5))로만 확인된다.

강제 장치 3건: 키 `deepEqual` 게이트(§15.10.4의 T91식 패턴 재사용) · `hasVerifyIntercept` 일관성 단언 · **분포 5/4/4 고정**(누가 한 행을 `reduced`로 바꾸면 테스트가 먼저 깨진다).

### (E) L4 — "미루기"가 아니라 "2단으로 나누기"

**고급의 요구는 2단이다: 무해해 보이는 선행 요구 → 최종 요구.** 하드 제약 셋:

1. **선행 요구도 구체적 행동 지시여야 한다.** `SCENARIO_PROGRESSION`의 *"대화 초반 2~3턴 안에 지금 당장 무엇을 해야 하는지 지시한다"* 는 **선행 요구에 적용된다.**
2. **선행 요구를 새로 발명하지 않는다** — 이 훈련이 이미 재현하는 것(본인확인 항목, 안내 문자·링크 확인, 조회용 모의 앱 설치) 안에서만 고른다. 신규 요구 형태는 곧 신규 무해화 검증 표면이다(AC-072가 "신규 가짜 화면 계열 금지"로 세운 원칙과 동형).
3. **현행 고급 문구 `"요구에 더 빨리 도달한다"`(`promptAssembly.ts:114`)를 삭제한다** — L4와 정면 모순이라 두면 L4를 구현해도 발동하지 않는다.

**왜 이렇게까지 못 박는가(실측 근거).** `promptAssembly.ts:27-39` 주석이 기록한 사용자 실측 신고 — **12개 시나리오 전부가 구조적으로 요구에 도달할 수 없었고**, `"요구 얼버무리기"` 지시가 요구 자체를 금지하고 있었다. L4를 "지연"으로 쓰면 그 결함이 **가장 정교해야 할 고급에서만** 재발한다.

### (F) 폴백 — §15.10.8 옵션 A(범위 축소) + 파생 기록

**옵션 A 채택.** `reduced` 4종은 고급에서 L3를 내지 않되 L1·L2·L4가 전부 적용되므로 "중급처럼 동작"하지 않는다. 원안의 전제(*"D3/D4를 가진 시나리오가 0개"*)는 이 설계의 9/13에서 성립하지 않는다 — **D4가 콘텐츠가 아니라 레버**이기 때문이다.

- **옵션 B(선택 목록 제외) 기각** — §15.10.8 근거 + **AC-064 명문 위반**(*"난이도는 시나리오 목록을 필터링하지 않는다"*). 게다가 빠지는 4종이 전부 가족·지인 사칭이라 Target Users의 핵심 분기가 고급에서 통째로 사라진다.
- **옵션 C(사용자 고지) 기각** — §15.10.8 근거 + 훈련 내부 사정 노출이 D-6/AC-066 취지와 어긋난다.
- **축소 사실을 프롬프트에 쓰지 않는다** — `ADVANCED_L3_REDUCED`는 빈 블록이다. 문구를 저작하면 모델이 그것을 대사로 흘릴 위험이 있다.
- **기록은 파생 순수 함수 `isL3Applied(scenarioId, level)` + 분포 테스트**다. `sessions/{}` 신규 필드도 `createRealtimeCall` 응답 증분도 만들지 않는다 → **Database.md·API.md 무변경 = AC-077 무스키마 유지.** 파생 가능한 값을 저장하면 드리프트 원천이 된다(§15.4.1이 역정규화 컬렉션을 기각한 것과 같은 논리).

### (G) AC-076의 D4 공백 — `loan-refinance-scam`

`SCENARIO_AXES`는 **중급 기준선 좌표표**이며(§15.3.1의 "현행 프롬프트 = 중급"과 동형) 난이도 오버레이를 써 넣지 않는다. 따라서 AC-076의 D4는 **콘텐츠로 채워야 한다.** 대상은 임의 선택이 아니다 — **PRD 근거 데이터 #5가 이름으로 지목**한다: *"대출빙자형 61% 증가 … 실제 상담처럼 **서류까지 갖춰** 의심 최소화 … **현행 `loan-refinance-scam`은 즉석 압박형**"*. T85는 이 1종에 D4 라벨 1개 + 축 값 1개를 더하고 `DECLARED_COVERAGE_GAPS`의 D4 행을 삭제한다. **§17.1의 D5 언더카운트 정정과는 다른 사안이며 T85는 전자만 한다.**

## Consequences

**긍정**
- 축 표의 정확도가 **난이도의 정확도와 분리**된다 — 커버리지 목적의 좌표 수정이 라이브 프롬프트를 바꾸지 않고, 그 역도 성립한다.
- **9/13 시나리오의 고급이 실제로 D3 또는 D4를 갖는다**(콘텐츠 저작 0벌, 신규 메커닉 0건).
- Database.md·API.md·`firestore.rules`·인덱스·화면 **전부 무변경**. AC-077 회귀 표면이 사실상 0.
- 초급=상한 / 고급=하한이라는 비대칭이 AC-065를 문구가 아니라 **구조**로 한 겹 더 보증한다.
- T83이 세운 자동 테스트 2건이 **무개정으로** 새 블록까지 커버한다(전수 순회 구조 덕분).

**부정·트레이드오프(정직 고지)**
- **`L3_DEPTH_TABLE`이라는 손으로 유지하는 표가 하나 늘었다.** 축 표를 안 읽는 대가다. 다만 이것은 *처방*이라 "콘텐츠보다 좁을" 수 없고, 키 게이트·일관성 단언·분포 단언 3겹이 걸린다.
- **가족·지인 사칭 4종의 고급은 L3를 받지 못한다.** L1·L2·L4로 정교해지지만 축 D 깊이는 그대로다 — 이 4종을 무엇으로 더 정교하게 만들지는 콘텐츠 기획 판단이며 이번 범위 밖이다(**OQ-A12**, planner).
- **`l3Procedural`을 호출부 3곳 중 하나라도 빠뜨리면 그 경로만 조용히 축소된다**(§15.6 G5와 같은 부류, **G63**). 기본값이 `reduced`라 에러 없이 일어난다 — T85 완료 증거에 **경로별 단언**을 필수로 넣는다.
- **ElevenLabs 경로(clone 2종)는 난이도 자체가 미적용**이라(§15.3.3) `isL3Applied`만 보면 원인을 오해할 수 있다(**G65**).
- **AC-074의 검증 조건 "최소 2회 이상 서로 다른 근거·절차로 재대응"에 자동 측정 수단이 없다** — 프롬프트 문구로 지시했을 뿐이며 T87의 라이브 계수에 의존한다(**OQ-A13**).

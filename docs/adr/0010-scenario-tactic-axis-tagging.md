# ADR-0010: 시나리오 수법 축(A~E) 태깅의 소재지와 `tacticCategory`와의 직교성

- Status: accepted
- Date: 2026-07-26
- Owner: architect
- DECISIONS.md entry: #41
- 관련: PRD v1.6 "시나리오 수법 축 체계" · AC-070/AC-076/AC-077 · MVP #28 / UX.md **D-46** · **OQ-U25** / Architecture.md **§15.10** / Tasks T78 → T81·T82
- 관계: 기존 ADR을 하나도 뒤집지 않는다. ADR-0004(프롬프트 서버 소유)·ADR-0003(폐기)·ADR-0005/0006(2인)과 접점이 없다. **§0 원칙 4**(송금·계좌 개념 부재)와의 정합은 Decision 절에서 명시 확인한다.

## Context

PRD v1.6은 시나리오 라이브러리를 5개 축(A 접근 경로 / B 사칭 주체 / C 압박 기제 / D 이탈 차단 / E 요구 형태)으로 분해하고, **AC-070**으로 (i) 모든 시나리오의 5축 태깅, (ii) 축 값이 **고정 열거형**일 것, (iii) 태깅 없는 시나리오는 등록되지 않을 것, (iv) 라이브러리 전체 커버리지 산출을 요구한다. **AC-076**은 여기에 *"잔여 공백을 명시 기록하며 조용히 누락하지 않는다 — 커버리지 산출물이 E4를 0건으로 드러내지 못하면 미충족"* 을 얹고, **AC-077**은 *"기존 식별자·메타 무변경, 과거 리포트·아카이브 무소급"* 을 요구한다.

세 가지 힘이 서로 당긴다:

1. **UX가 축의 화면 노출을 전면 금지했다(D-46).** 축은 기획·커버리지 프레임이지 사용자 어휘가 아니며, 카드에 이미 "성향"·"난이도" 2종 표기가 있어 축을 얹으면 AC-067이 막으려던 표기 3중화가 된다. UX는 *"`ScenarioMeta`의 사용자 노출 필드가 아니라 내부 태깅·커버리지 산출용으로만 설계하면 된다"* 는 인계를 남겼다.
2. **시나리오 메타는 미러 2벌 구조다.** `functions/src/scenarios/publicMeta.ts`(seed 소스, Firestore `scenarios/{}`로 주입)와 `src/content/scenarios/*.ts`(클라)가 손으로 동기화되며, 드리프트 테스트가 있다. 그런데 **그 테스트가 실제로 지키는 범위는 1/13 시나리오 × 3필드**이고(`scenarios.test.ts:108-120`), **두 미러는 지금 이미 `callerLabel`에서 13/13 어긋나 있다**(T75가 클라만 갱신, 테스트가 그 필드를 안 봄).
3. **`tacticCategory`(T74, 고정 10종)와 이름이 겹쳐 보인다.** 축 C/D의 값과 `verification_block`·`urgency` 같은 카테고리는 어휘가 유사해 "같은 것을 두 번 만드는 것 아닌가"라는 의문이 UX **OQ-U25**로 남았다.

## Decision

**축 태깅은 `functions/` 안 단일 소스 상수 모듈에만 두고(미러 0벌·Firestore 0필드·클라 계약 0), 커버리지는 그 상수를 열거형 전 도메인으로 순회하는 순수 함수가 빌드타임에 산출하며, 축과 `tacticCategory`는 직교 개념으로 영구 분리한다.**

### (1) 소재지

| Option | Pros | Cons |
|---|---|---|
| **`functions/src/scenarios/axes.ts` 단일 소스(채택) ✅** | `scenarios/{}`가 클라 read 허용 문서(`firestore.rules:63-67`)라는 사실 때문에, 화면 계약 밖에 두는 것이 **D-46을 "안 그리기"가 아니라 "가질 수 없음"으로** 만든다 · 미러가 없으니 드리프트가 **불가능** · Firestore 스키마 0 변경 → **재시딩 불요**, 커버리지가 배포 상태와 무관하게 정확 · AC-077 회귀 표면이 사실상 0 | 시나리오 하나의 사실이 두 파일로 나뉜다(추가 시 손댈 곳 +1) — `deepEqual` 키 게이트가 잊으면 즉시 실패로 만들어 회수 |
| `ScenarioMeta`/`ScenarioDoc` 옵셔널 증분(미러 2벌) | 시나리오 사실이 한 곳에 모임 · 기존 옵셔널 증분 관례(`channel`/`surface`/`escalation`)와 형태 동일 | **드리프트 방어가 실측상 존재하지 않는다**(1/13 × 3필드) — 축 65칸을 그 위에 얹는 것은 없는 방어에 얹는 것 · 클라 read 허용 문서에 축이 들어가 D-46이 규율(discipline) 문제로 격하 · 재시딩 필요 · `estimatedDuration` 등과 달리 **사용자에게 보여줄 일이 영원히 없는 값** |
| Firestore 신규 컬렉션(`scenarioAxes/{}`) | 콘텐츠와 좌표 분리는 동일 | 커버리지가 시딩 상태에 종속되어 **CI에서 AC-076을 검증할 수 없다** · read 경로·규칙 표면 증가 · 얻는 것 0 |

### (2) 열거형과 `D0_none`

축마다 `as const` 배열 + 파생 union(저장소 관례 — `TACTIC_CATEGORIES`·`DIFFICULTY_LEVELS`와 동형). 값 이름은 `<PRD코드>_<의미>`(예 `D3_verification_hijack`) — 코드만이면 `D2`↔`D3` 오타가 안 보이고(의미가 정반대다), 의미만이면 AC-076 문면과 대조가 안 된다.

**축 D에 `D0_none`을 둔다.** PRD 매핑 표는 4종의 D열에 "(없음)"을 적었는데 AC-070은 "각 축 최소 1개"를 요구해 **문면이 충돌**한다. 빈 배열 허용은 **"수법 없음"과 "미태깅"을 구분 불가**로 만들어 AC-070을 무력화하고(부재를 판별자로 오버로드하는 안티패턴 — §14.8.1·§14.9.1이 이미 두 번 기각), 그 4종에 D 값을 새로 배정하는 것은 콘텐츠를 안 바꾸고 좌표만 바꾸는 **거짓 태깅**이다. `D0_none`은 새 수법을 발명한 것이 아니라 PRD가 이미 쓴 "(없음)"에 표현형을 준 것이며, 덤으로 AC-074 L3의 *"초급 = 축 D 수법 0~1개"* 의 "0개"가 표현 가능해진다. **축 정의 표에 닿는 값이므로 planner 비준을 요청한다**(구현은 막지 않는다).

**§0 원칙 4 정합 확인**: `E1_transfer_demand`는 **분류 어휘**이지 금전을 움직이는 필드·엔드포인트가 아니다. 동일 판단의 선례가 이미 있다 — `TACTIC_CATEGORIES`의 `"payment_demand"`(`report/tacticCategory.ts:39`).

### (3) 커버리지 산출

**빌드타임 상수 순회(순수 함수).** 런타임 집계·콜러블·화면을 만들지 않는다(커버리지 대시보드는 D-45/D-46 정면 위반이며 UX v1.12가 *"커버리지 산출물은 빌드·테스트 산출물이지 화면이 아니다"* 로 못 박았다).

**AC-076의 유일한 성립 조건은 "태깅된 값이 아니라 열거형 전 도메인을 순회"하는 것이다.** 데이터를 순회하며 카운트를 올리면 0건 값은 **키 자체가 생기지 않아 E4가 조용히 사라진다** — AC-076이 명시한 바로 그 미충족이다. 여기에 사유를 담은 `DECLARED_COVERAGE_GAPS` 선언 표와 **양방향 `deepEqual`**(계산된 0건 집합 ↔ 선언 집합)을 걸어, 공백이 **사라지는 것**과 **조용히 채워지는 것**을 동시에 막는다.

### (4) 태깅 누락 강제

타입 2겹(5축 required + `readonly [T, ...T[]]` 비어 있지 않은 배열) + **T91식 `deepEqual` 키 1:1 게이트**. 타입만으로는 불가능하다 — `PUBLIC_SCENARIOS`가 `Record<string, ScenarioMeta>`라(`publicMeta.ts:241`) TS가 망라성을 검사할 수 없고, 리터럴 union 키로 바꾸려면 8개 파일에 파급되는 공용 타입 리팩터가 되어 AC-077 위험 대비 이득이 없다. **T91에서 가져오는 것은 키 `deepEqual` 게이트뿐이고, 손으로 지명한 문자열 라벨 + `startsWith` 검사는 가져오지 않는다** — T91이 문자열을 쓴 이유는 단언 대상이 자유 저작 산문 안에 있었기 때문이며, 축 값은 처음부터 열거형이라 멤버십을 컴파일러가 본다.

### (5) `tacticCategory`와의 관계 — **직교(OQ-U25 판정)**

| | 축(A~E) | `tacticCategory`(10종) |
|---|---|---|
| 부착 대상 | `scenarioId` = 콘텐츠, **설계시 상수** | `DeceivedMoment` = 한 세션의 한 순간, **런타임 관측값** |
| 기수 | 시나리오 1개 → 축 값 1~3개(고정) | 세션 1개 → 순간 0~n개. **축→카테고리는 함수가 아니다** |
| 정규화 방향 | **사전 선언형**, `other` 폴백이 **없어야** AC-070이 성립 | **사후 흡수형**, `other` 폴백이 **있어야** 드리프트 테스트가 성립(§15.4.2) |
| AC-077 | 병합하면 과거 리포트의 묶기 의미가 바뀌어 **소급 수정에 해당** | 직교면 `DeceivedMoment`에 필드가 0개 추가 → **소급이 구조적으로 불가능** |

금지 3건: `DeceivedMoment`에 축 필드 금지 · `TACTIC_CATEGORIES`에 축 코드 금지 · 두 모듈 상호 import 금지. 명명 규칙으로 혼동 차단: **축 값은 항상 코드 접두사를 갖고, `tacticCategory` 값은 절대 갖지 않는다.**

신규 순간 2종은 **기존 값에 매핑하며 enum append는 하지 않는다** — 모의 앱 설치 → `link_or_install`, 확인 무력화 → `verification_block`(기법은 정반대지만 묶기의 목적은 *"참가자가 반복해서 넘어가는 지점"* 이고, 분리하면 "확인 관련 3번"이 "2번+1번"으로 흩어져 §15.6 G14가 재발한다). 단 **`CATEGORY_RULES`의 정규식 2행은 확장이 필요하다**(실측: `:53`에 "원격" 없음, `:62`에 확인 *권유* 계열 없음) — 이는 **값 목록 변경이 아니라 규칙표 행 확장**이며 둘을 혼동하면 안 된다.

## Consequences

- **Positive**
  - **AC-077을 "지키자"가 아니라 "깰 수 있는 경로가 없다"로 만든다** — 리포트·아카이브 스키마에 필드를 하나도 추가하지 않으므로 소급 수정이 구조적으로 불가능하다. Database.md·API.md·`firestore.rules`·인덱스 전부 무변경.
  - **D-46이 규율이 아니라 구조가 된다** — 축이 클라 계약에 존재하지 않아 "실수로 화면에 그리는" 경로가 없다.
  - 커버리지가 **CI에서 깨질 수 있게** 되어 AC-076의 "조용한 누락 금지"가 문서 약속이 아니라 빌드 게이트가 된다.
  - 기계 산출이 **손으로 만든 PRD 표의 오류를 즉시 드러냈다** — A4가 0건인데 공백 표에 없다는 점, B1 count가 2가 아니라 3이라는 점(§15.10.9 G35/G36). 축 체계의 존재 이유가 도입 시점에 이미 증명됐다.
- **Negative / accepted trade-offs**
  - 시나리오 하나의 사실이 `publicMeta.ts`와 `axes.ts` 두 파일로 나뉜다. 시나리오 추가 시 손댈 곳이 하나 늘어나며, 잊으면 `deepEqual` 게이트가 잡는다(잡지 못하는 것은 **값의 정확성**이다 — 아래).
  - **가드는 "축 값을 가졌다"만 증명하고 "값이 맞다"는 증명하지 못한다.** `courier-customs-scam`에 `D0_none` 대신 `D2_secrecy`를 적어도 전부 통과한다 — T91이 자기 가드에 대해 적은 한계와 **완전히 같은 종류**이며, 그래서 표를 손으로 유지하고 각 행에 근거 주석을 요구한다.
  - 축 값을 화면에 쓰고 싶어지는 날이 오면 미러 도입이 필요하다 — 그때는 **미러를 만들 게 아니라 D-46 재검토가 먼저**다(§15.10.9 G37).
- **Follow-ups required**
  1. **T82**: `axes.ts`(13종 정본 표 = §15.10.7) · `axisCoverage.ts` · `axisCoverageReport.ts` · `deepEqual` 키 게이트 · 양방향 공백 `deepEqual` · `npm run report:axis-coverage` 스크립트.
  2. **T81**: `SCENARIO_AXES[].exitBlock`을 L3 입력으로 사용. **현재 D3/D4 보유 시나리오가 0개**이므로 부재 시 폴백 규칙을 명시할 것(조용히 중급처럼 동작 금지).
  3. **T83/T84**: `TACTIC_CATEGORIES` 값 목록은 건드리지 말고 `CATEGORY_RULES` 행 정규식만 확장(§15.10.5).
  4. **planner**: `D0_none` 축 정의 표 등재 비준(G32) · A4 0건 공백 채택 여부(G35) · B1 count 2↔3 정정(G36). **셋 다 T82 착수를 막지 않는다.**
  5. **별건(implementer)**: `callerLabel` 미러 드리프트 13/13 정리 + 드리프트 테스트 범위 확대(G38) — T78 범위 밖.

## 2. 설계안 (기획 — 결정 전 초안)

### 2.1 난이도별로 다르게 할 축 (판정표)

> 원칙: 난이도는 "같은 대본을 세게/약하게 말하기"가 아니라 **다른 수법·다른 흐름**을 고르는 것이다.
> 안전·무해화 경계(AC-005/013/032/033/065)는 세 난이도에서 동일하다 — 아래 표의 어떤 칸도 그것을 바꾸지 않는다.

| 축 | 초급 — 전통형 | 중급 — 혼합형 | 고급 — 최신형 |
|---|---|---|---|
| **수법 종류** | 단일 수법·단일 사칭(검찰·금감원 사칭, 대출 빙자, 가족 사칭) | 전통형 + 한 가지 변형(카드 배송 사칭→가짜 카드사, 메신저 선접촉→전화) | 복합 수법: 여러 사람 릴레이, 앱 설치 유도(모의 화면), 가짜 확인 전화, 메신저+전화 결합, 현금 전달 요구, 고립(혼자 있게 하기) |
| **사기범 인원** | 1명 | 1명(필요 시 "상급자 바꿔 드릴게요" 1회) | 2~3명 릴레이(예: 카드사 상담원 → 금감원 직원 → 검사) |
| **채널** | 전화만 | 전화 + 문자 | 전화 + 문자 + 메신저/모의 앱 화면 |
| **압박 강도** | 약함 — 의심하면 물러선다 | 중간 — 한 번 더 밀어붙인다 | 강하지만 침착 — 절차·서류로 정당화, 공포보다 "도와주는 척" |
| **주도권 배분** | 사기범은 묻고 기다린다. **사용자 발화 1회당 사기범 발화 1회**, 연속 발화 금지 | 같음(연속 발화 금지). 사기범이 화제를 이끈다 | 같음(연속 발화 금지). 사기범이 화제를 강하게 이끌되 사용자 질문엔 반드시 답한다 |
| **문자·도구 빈도** | 0~1통. 최종 요구 한 번에만 | 1~2통. 종류·순서는 대화 흐름에 따라 | 0~3통 + 다른 표면(모의 앱·메신저·가짜 확인 창구). **문자 없이 진행하는 변형도 있다** |
| **문자 순서** | 고정 아님 — 요구 단계에 도달했을 때만 | 흐름 의존(본인확인 단계에서 OTP, 이체 단계에서 계좌) | 변형마다 다름(OTP 없이 앱 설치 → 확인 전화 가로채기 등) |
| **의심 신호의 노골성** | 노골적 — "기관이 전화로 이체 요구", "안전계좌", 어색한 말투 등 교과서 신호 2개 이상 노출 | 중간 — 신호 1~2개, 나머지는 그럴듯함 | 은밀 — 신호가 절차 속에 숨는다(확인을 권함, 공문 이미지, 실제처럼 들리는 부서명) |
| **이탈 차단** | 시간 압박 1가지만(현행 초급 L3 상한 유지) | D1·D2·D5(현행) | D3(확인 무력화)·D4(절차 정당화)·고립 지시 |
| **요구 단계** | 1단(처음부터 최종 요구) | 압박 후 최종 요구 | 선행 요구 → 최종 요구(현행 L4 유지) + 릴레이마다 요구 이양 |

- 주도권 행의 "연속 발화 금지"는 **모든 난이도 공통**이다. 사용자 신고 1의 직접 처방이다(§2.3).
- 고급의 "강하지만 침착"은 현행 `ADVANCED_BASE`(`promptAssembly.ts:441-448`)·`ADVANCED_L3_PROCEDURAL`(`:490-495`)과 방향이 같다 — 버리지 않고 **흐름 변형 위에 얹는다**.

### 2.2 시나리오 구조 — "시나리오 × 흐름 변형"

현재는 시나리오 1종 = 프롬프트 1벌 = 문자 순서 1벌이다. 이것을 **시나리오 1종 = 흐름 변형 여러 벌**로 바꾸고, 난이도가 고를 수 있는 변형을 정한다.

| 구성 요소 | 지금 | 제안 |
|---|---|---|
| 시나리오(사칭 주체·상황) | 14종 | 14종 유지 + 고급 전용 복합 시나리오 신설(개수는 §4 D2) |
| 흐름 변형(flow variant) | 없음 | 시나리오마다 2~3벌. 각 변형 = {단계 목록, 허용 문자/표면, 인원 구성, 의심 신호 수준} |
| 변형 선택 | — | 세션 생성 시 서버가 **난이도에 허용된 변형 중 하나를 고른다**(무작위 또는 회전 — §4 D6). 세션 문서에 변형 id 기록 → 리포트·리플레이가 같은 변형으로 해석 |
| 수법 목록 | 시나리오당 1벌 | 공통 수법 + **변형별 수법**. 초급 변형은 이탈 차단 수법을 아예 포함하지 않는다(문면 충돌 문제 5 해소) |
| 문자 카탈로그 | 시나리오당 고정 배열 | 변형별 "허용 문자 집합" + 각 문자의 **도달 조건**(§2.4) |

예시 — `institutional-impersonation`:

| 변형 | 난이도 | 흐름 | 문자/표면 |
|---|---|---|---|
| I-1 전통형 | 초급 | 검사 사칭 → 대포통장 연루 → 안전계좌 이체 요구 | 계좌 문자 1통(이체 요구에 도달했을 때만) |
| I-2 본인확인형 | 중급 | 수사관 사칭 → 신원 확인 → 명의 도용 → 자산 보호 이체 | OTP(본인확인 단계) · 계좌(이체 단계) — 사용자가 OTP를 거부하면 OTP 없이 이체로 |
| I-3 릴레이·가로채기형 | 고급 | 카드 배송 문자/전화 → 가짜 카드사 → "명의 도용, 금감원 연결" → 금감원 직원 → 검사 → 보안 앱 설치(모의 화면) → 확인 전화를 걸면 가로채기 | 링크 문자 · 모의 앱 설치 · 확인 창구(현행 D3 메커닉 재사용) · 마지막에 현금 전달 또는 이체 |

### 2.3 주도권 — 연속 발화 제거 설계

| # | 규칙 | 적용 위치(구현 단계에서 확정) | 메모 |
|---|---|---|---|
| T1 | **문자 도착 안내는 사용자 차례를 건너뛰지 않는다.** 문자는 즉시 화면에 도착시키되, 사기범이 그 사실을 말하는 것은 **다음 사용자 발화 뒤의 응답**에 싣는다 | 실시간: 지시를 `turnComplete:true` 턴이 아니라 **응답을 유발하지 않는 맥락 주입**(`turnComplete:false`, 기존 `personaStateTurn`과 같은 방식)으로 넣는 안. 폴백은 이미 응답에 섞이므로 유지 | 근거: `clientTurnQueue.ts:11`이 *"`turnComplete:false` 주입은 응답을 유발하지 않고 생성을 끊지도 않는다"* 고 적고 있다(최초 실측 §25.3 (4) P-1). ⚠️ 다만 **문자 안내 용도로, 그리고 다음 사용자 발화 뒤 응답에 실제로 반영되는지**는 실측한 적이 없다 → **3.8 프로브 필요**. 실패 시 대안: 사용자 발화가 올 때까지 지시를 보류(큐에 `waitForUserTurn` 조건 추가) |
| T2 | **지시로 생긴 발화는 사기범 턴으로 세지 않는다** — 문자 시점 계산은 "사용자 발화 수" 기준으로 바꾼다 | `onScammerTurnComplete` 계수 기준 | P2 해소. 리포트 앵커(`anchorScammerTurn`)와의 정합은 architect 판정 필요 |

| T4 | **백스톱은 '강제 발송'이 아니라 '건너뛰기 가능'** — 대화가 다른 쪽으로 갔으면 그 문자는 보내지 않는다 | `toolWindow.ts` 판정 | 고급의 "문자 없는 변형"과 정합 |
| T5 | announce 문면에서 "재촉하라"를 빼고, 문자를 보냈다는 사실 1문장 + 상대 반응 대기 | `inCallSms.ts` announce 문면 | P5·R4 해소 |

### 2.4 문자 발송 — 고정 순서 대신 "도달 조건"

| 문자 종류 | 도달 조건(모두 충족 시 발송 가능) | 초급 | 중급 | 고급 |
|---|---|---|---|---|
| OTP(본인확인) | 사기범이 본인확인을 요구했고 + 사용자가 거부하지 않았고 + 직전 문자 뒤 사용자 발화 ≥2 | 미사용 | 사용 | 변형에 따라(앱 설치 변형은 미사용) |
| 계좌(이체) | 사기범이 이체를 구체적으로 요구했고 + 직전 문자 뒤 사용자 발화 ≥2 | 사용(유일한 문자) | 사용 | 사용 또는 현금 전달로 대체 |
| 링크(신청·보안 앱) | 사기범이 링크/앱을 언급했고 + 직전 문자 뒤 사용자 발화 ≥2 | 미사용 | 시나리오별 | 사용(모의 앱 설치와 연결) |

- 모델이 고르는 방식: `send_prepared_sms`에 **목적 인자**(`purpose: "identity" | "transfer" | "link"`)를 추가하고, 서버가 그 세션 변형의 허용 집합·도달 조건으로 재검증한다. 인자 없는 현행(`liveTools.ts` `parameters: {}`)은 카탈로그 순서를 강제하는 구조라 순서 다양화가 불가능하다.
- 도달 조건 판정 원천: 1차는 모델의 도구 호출(모델이 "지금 이체를 요구했다"고 판단), 2차는 서버 재검증(최소 간격·허용 집합). **대화 내용 분류기는 새로 만들지 않는다**(비용·지연 — §4 D7에서 확정).

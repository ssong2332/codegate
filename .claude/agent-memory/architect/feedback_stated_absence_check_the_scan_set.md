인계문이 *"grep 0건 ⇒ 모델의 순수 애드리브"* 라고 하면, **결론이 아니라 스캔 집합을 먼저 재검증한다.** 같은 지시가 어느 층에 복제돼 있을 수 있는지 물은 뒤 다시 grep한다.

**Why:** 사용자 프로덕션 신고에서 상류가 *"`promptAssembly.ts`에 '통화 종료' 관련 지시 0건 ⇒ 애드리브"* 로 인계했는데, `functions/src/scenarios/*.prompt.ts` **14/14 전부**에 *"세션은 짧게 … 마무리되도록 진행한다"* 가 있었다. 상류가 거짓을 말한 게 아니라 **한 파일만 봤다**. 이 저장소는 프롬프트가 **공유 조립 블록 1벌 + 시나리오 14벌 + 카탈로그 지시문(inCallSms/verifyIntercept의 `announceInstruction`)** 세 층으로 나뉘어 있어 한 층만 보면 반드시 놓친다.

같은 패스에서 **같은 형태가 하나 더** 나왔다: *"§43이 `:296`을 조건화했는데도 뚫렸다 ⇒ 문면 층의 반복 실패"* → 실제로는 같은 취지의 지시가 `:51`·`:83`에 **아직 조건화되지 않은 채** 살아 있었다. ⇒ **"2회 실패"가 아니라 "1회 실패 + 미패치 2곳"** 이었고, 층을 바꿀 시점이 아니었다([[prompt-layer-two-strikes]]의 발동 조건 판정에 이 확인이 선행한다).

**How to apply:**
1. "0건" 인계를 받으면 **grep 대상 파일 목록을 보고에 명시**하고, 빠진 층이 있는지 확인한 뒤 다시 친다.
2. "이미 고쳤는데 재발" 인계를 받으면 **고친 자리의 블록 범위**를 확인한다 — 난이도 블록 안의 수정은 다른 난이도에 안 나간다.
3. 결론이 *"모델 애드리브"* 나 *"프롬프트 층 소진"* 이면 특히 의심한다 — 둘 다 **더 파지 않아도 되는 결론**이라 스캔이 좁을 때 나오기 쉽다.

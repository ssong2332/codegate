상류(UX)가 새 상태 기록을 "기존 X 기록과 같은 범위가 자연스럽다"고 권하면, **범위(저장소·수명·삭제 시점)는 따르되 키는 분리**하는 것이 기본이다. 키를 공유하면 그 키를 읽는 **다른 라우트의 게이트**가 새 기록을 자기 사실로 오인한다.

**Why:** T187(2026-10-17) — 메신저 시작 고지 확인 기록을 `markSessionAnswered`(`session.answeredSessionId`)와 같은 범위로 두라는 UX 의견. 그 키를 통화 화면이 에스컬레이션 세션의 "받기 끝남" 판정에 **단독으로** 쓴다(`play/page.tsx` isEscalated 분기) → 공유하면 메신저→통화 도착 시 벨 화면 프리롤을 건너뛴다 = T30이 고친 회귀 재발 + OQ 확정 전 현행 유지 위반. 소스를 읽기 전에는 "같은 범위 = 같은 키"로 읽기 쉬웠다.

**How to apply:** 저장 위치 인계를 받으면 ① 기존 키의 **읽기 지점 전수 grep** ② 각 읽기 지점이 무엇을 판정하는지 ③ 새 기록이 참일 때 그 판정이 어떻게 바뀌는지 표로 확인. 읽기 전용 교차 참조(새 화면이 기존 키를 *읽기만*)는 허용하되 쓰기 금지를 게이트로 건다(G450 형태). [[overloaded-flag-judge-by-live-extension]]와 같은 계열.

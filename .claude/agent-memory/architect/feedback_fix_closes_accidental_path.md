수정이 **결함이 우연히 열어 둔 사용자 경로**를 닫는 경우가 있다. T181(2026-10-02): 챌린지가 `completed`로 안 바뀌던 동안 수신자는 완료 후 링크를 다시 열어 *재개* → 리플레이·결과 공유·신고에 다시 닿을 수 있었다. 전이를 넣으면 랜딩(`join/page.tsx:74-80`)과 동의 게이트(`consentGate.ts:57-58`)가 이미 구현해 둔 대로 *차단*이 된다.

**Why:** "동작이 바뀐다 = 회귀"로 읽으면 멀쩡한 게이트를 고치게 된다. 반대로 "설계대로다"로만 닫으면 사용자가 실제로 잃는 것(재방문 경로)이 보고에서 사라진다. 그 경로에 기대던 **검증 절차**도 조용히 무효가 된다 — T177 ⑧의 §66.5 재개 경로 라이브 확인은 *완료 뒤* 재동의로 얻은 것이라 T181 뒤에는 차단을 관측한다.

**How to apply:**
1. 판정 근거는 **원 설계 문장 + 그 동작을 구현한 코드 주석**(이번엔 §14.4 *"재개는 in_progress에서만"* + 두 층의 주석)이다 — 있으면 "설계 복구", 없으면 회귀 후보.
2. "오늘(결함) / 수정 후" 진리표로 **사라지는 것**을 행으로 적고, 어떤 AC도 그것을 요구하지 않으면 결함이 아니라 **제품 결정 → OQ(ux)** 로 분리하고 기본값은 현행 설계로 둔다.
3. 그 경로를 밟던 기존 검증 절차·라이브 증거를 grep해 **무효화 여부와 새 재현 조건**(예: 세션이 active일 때 재진입)을 적는다.
4. 노출이 늘어나는 수정이면(미동의여도 "완료" 사실이 보임) "설계된 노출의 복구인가, 확대인가"를 응답 필드 무변경으로 보인다. 관련: [[conflict-moves-to-adjacent-line]], [[wording-must-hold-in-every-emitting-state]].

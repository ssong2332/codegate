번호는 **두 번 잰다 — 착수 시점과 병합 직전.** 한 번만 재면 동시 패스와 반드시 충돌한다.
인계문이 *"방금 §N·G-M·OQ-X·#K가 병합됐다"* 라고 말해도 그대로 쓰지 말고 **직접 전수 grep**하되,
**내 실측이 나중에 낡는다는 것도 함께 계산하라.**

**Why:** 2026-07-29 패스에서 두 가지가 같이 일어났다.
1. 착수 시 인계값(`§43·G236·OQ-A33·#78`)이 실측(`§42·G221·OQ-A30·#74`)보다 **앞서 있었다** —
   기존 5회의 "예약·소진"과 다른 **여섯 번째 형태**. 인계가 인용한 판정 문장도 grep 0건이었다.
2. 그런데 작업 중 `main`이 전진해 **그 인계값이 실제로 도착했다**(§43 병합). 내 실측도, 인계값도
   각자의 시점에서는 옳았다. ⇒ *"누가 틀렸나"* 가 아니라 **"어느 시점인가"** 가 정답이다.
결국 오케스트레이터가 §45·G244~G253·OQ-A35/36·#80으로 재배정했고, 나는 **배정값이 실제로
비어 있는지 직접 재검증**한 뒤 옮겼다.

**How to apply:**
- 계열별 grep 패턴을 그대로 쓴다: 절 `^#{2,3} `, 게이트 `G[0-9]{3}`, `OQ-A[0-9]+`,
  DECISIONS 표 행 `^\| [0-9]+ \|`. **`-o` + `head_limit`** 로 최대값만 뽑는다.
- 인계문이 *"§N이 X를 확정했다"* 라고 인용하면 **그 X 문자열 자체도 grep**하라 — 절 번호는
  맞는데 내용이 없거나, 절 자체가 없을 수 있다.
- 워크트리와 메인 체크아웃 **양쪽**을 본다. `.git/refs/heads/main`은 **셸 없이 Read로 읽힌다** —
  base 확인에 `git log`가 필요 없다.
- **리넘버가 오면 기계적 전역 치환을 하지 마라.** `xxx.ts:43` 같은 **파일 줄번호**와 **다른 절 인용**이
  같은 숫자를 쓴다. 안전한 순서: `### N.` → `## N.` → `§N.` → `§N` (긴 것부터, 접두 포함 관계 주의).
- **리넘버 기록을 남겨라.** 검산에서 옛 번호 0건을 만들려고 *"원래 §43으로 잡았다"* 는 이력까지
  지우면 감사 흔적이 사라진다. **남은 히트를 0으로 만들지 말고 "왜 남았는지"를 열거**하라.
- 절에 **"번호 기준 시점"과 "줄번호 기준 시점"이 다를 수 있음**을 기준선에 명시하라. 재배정 뒤에는
  번호는 새 base, 인용 줄번호는 옛 base인 상태가 흔하다 ⇒ 착수 0단계에 줄번호 재검증을 넣는다.

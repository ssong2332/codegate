**지시문이 *"X가 없어서 못 한다"* 를 최대 제약으로 제시하면, 설계를 시작하기 전에 X의 실재부터 확인한다.** 확인 수단이 없으면 **"미확인 전제"로 명시하고 후보를 그 축으로 쪼개 둔다**(있을 때 안 / 없을 때 안).

**Why:** T106(2026-07-29). 지시문이 *"⛔ 가장 큰 제약 — 라이브 사본을 읽으려면 API 키가 필요하다"* 로 시작했는데, **키는 이미 있었고 에이전트 12개도 실재했다**(사용자가 지적해 패스 도중 정정). 그 결과 **판정 2건이 뒤집혔다**: ① 저장소가 강제하지 않는다는 이유로 기각했던 **이름 유도 매핑**이 라이브 12/12 일치 실측으로 **조건부 채택**이 됐고, ② 예산 단위가 **N콜 → 1+N콜**(목록 1회)로 바뀌었다. 반대로 *"키 없는 환경"* 설계는 죽지 않고 **"불가피한 한계" → "환경별 강등"** 으로 성격만 바뀌었다(격리 워크트리엔 `.env.example`뿐 — 실측).

**How to apply:**
- 자원 부재 주장은 **파일 존재·설정값·계정 상태**로 확인 가능한 경우가 많다(셸 없이 glob·grep으로도 된다). 워크트리에 없다고 저장소 전체에 없는 것이 아니다.
- 자원이 있는 것으로 밝혀져도 **부재 환경 설계를 지우지 말 것** — CI·새 clone·격리 워크트리는 여전히 부재다. 지우는 대신 **환경 × 동작 표**로 재분류한다.
- 기각했던 후보의 **기각 사유가 실측으로 소멸했는지** 재검토하라. 사유가 *"조용히 빠진다"* 류면, 실패를 **시끄러운 미실행(exit 2 + 전수 나열)** 으로 바꾸는 규칙만 붙여도 부활할 수 있다.
- 뒤집을 때는 원문을 고치지 말고 **뒤집힌 행/유지 행 전수표**를 새 절에 둔다([[feedback_judgment_may_already_be_a_section]] 형식).

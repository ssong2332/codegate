**순서·배치를 "하드 게이트"로 명문화할 때(예: *"게이트 A~E를 정밀화와 같은 커밋에"*), 각 게이트마다 "이 게이트가 참조하는 데이터가 그 커밋에 이미 존재하는가"를 먼저 확인한다.** 참조 대상이 나중 커밋에 들어오는 **참조 정합(cross-catalog reference) 게이트**는 앞 커밋에 넣으면 중간 커밋이 반드시 빨갛다 — 문면이 구조적으로 만족 불가능해진다.

**Why:** 이 프로젝트에서 architect **사후 추인(retroactive concurrence)이 두 번** 발생했고, 둘 다 내가 쓴 규칙이 실행 단계에서 그대로 성립하지 않아서였다.
- T83 **G58**(Architecture.md §16.6) — G31이 "문자 announce ↔ 확인 announce"만 고정하고 재연결 *대사*를 사각지대로 남겼다.
- T104 **G-B**(Architecture.md §19.8.1, ADR-0012 사후 노트) — G75가 *"G-A~G-E를 ①과 같은 커밋에"* 로 못 박았는데 G-B의 참조 대상(카탈로그 항목)이 ③에서 들어온다.

**How to apply:**
- 게이트를 배치할 때 **"이 게이트가 닫는 위험이 base에 이미 열려 있던 것인가, 이번 변경이 새로 여는 것인가"** 로 먼저 가른다. 새로 여는 위험(정밀화가 만드는 구멍) → 같은 커밋 강제, 예외 없음. **이미 열려 있던 위험** → **참조 데이터와 같은 커밋**(그보다 뒤는 금지). 이 두 행이면 대부분 갈린다.
- 앞 커밋에 억지로 넣으면 **공허하게 참인 단언**이 되는지 확인한다 — 대상 0건이면 그 게이트는 그 커밋에서 아무것도 안 잡으므로, 넣는 것이 오히려 "역검증 게이트"의 취지를 깬다.
- 구현자가 하드 게이트를 단독 재해석했으면 **재작업이 아니라 문서 위생**으로 처리한다: 판정 → Architecture.md 해당 갭 행 + ADR 사후 노트 + DECISIONS 신규 행. ADR은 immutable이므로 Decision을 고치지 말고 노트를 덧붙이고 원문 줄에 포인터를 단다.
- 일회성 추인으로 끝내지 말고 **if/then 판정표로 승격**한다(CLAUDE.md 1항). 같은 상황이 또 온다.

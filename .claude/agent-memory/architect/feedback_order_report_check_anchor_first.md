리포트/타임라인의 **순서 역전 신고**를 받으면, 런타임(턴 선택·발동 시점)을 건드리기 전에 **표시 층 2가지를 먼저 기계적으로 확인**한다.

1. **배치 앵커가 하나뿐인가** — 여러 사건(오퍼·전환·완료)이 한 항목에 묶여 **하나의 앵커**로 렌더되면, 뒤 사건이 앞 사건의 자리에 놓인다. 각 사건의 앵커 값이 **이미 문서에 저장돼 있는데 배치에 안 쓰이는지** 확인할 것(있으면 저장 스키마 델타 0으로 고칠 수 있다).
2. **이벤트 문면이 그 이벤트의 뜻과 일치하는가** — "카드가 떴다" 이벤트에 "넘겼다/완료했다" 문면이 붙어 있고 그 이벤트가 **무조건 방출**되면, 리포트가 **일어나지 않은 사건을 단언**한다. 조기 반환(조건 분기)이 문면 배열보다 **아래**에 있는지 보라.

**Why:** T-확인창구 순서 판정(2026-07-29)에서 사용자 신고 "전환이 예고보다 먼저 보인다"의 실제 원인은 런타임이 아니라 이 둘이었다. 배치 앵커가 오퍼 턴 하나뿐이었고(전환 앵커는 저장돼 있는데 판정용으로만 쓰였다), 전환 문면이 오퍼 이벤트에 붙어 조건 없이 방출됐다 — **참가자가 전환을 요청하지 않아도 리포트가 "넘겼습니다"라고 말했다.** 사용자 원문("내가 넘긴다고 한 적 없는데")이 비유가 아니라 사실 기술이었다.

**How to apply:** 층 판별표를 만들 때 표시 층 행의 증명 강도를 먼저 채운다 — 표시 층 결함은 **코드만으로 재현 가능(라이브 0회)** 이라 예산이 없는 날에도 확정할 수 있고, 런타임 층은 대개 "가능성 증명"에 그친다. 두 층은 고치는 파일이 겹치지 않으므로 **커밋을 분리**하고, "순서를 고쳤다"는 보고는 두 커밋이 다 있을 때만 허용한다.

**부수 판별자:** 붙여넣은 리포트의 **카드 개수**가 상태 판별자다(조건부 이벤트 카드가 없다 = 그 상태 필드가 비어 있다). 단 인용 축약 가능성이 있으므로 문서 필드 직접 확인을 프로브로 남길 것.

**"T92가 고친 자리에서 나온 후속 신고"처럼 선행 태스크가 있는 결함을 등재할 때는, 신고된 발화 문자열을 선행 게이트의 테스트 파일에 그대로 grep해 본다.** 히트하면 그 사실을 태스크 행의 별도 항목으로 올린다("기존 게이트와 정면 충돌").

**Why:** 2026-07-27 사용자 신고 *"질문을 한 턴에 몰아넣는다"* 의 발화 원문이 `functions/src/scenarios/__tests__/scenarios.test.ts:859`에 **오탐 0을 요구하는 "정상 문구" fixture로 박혀 있었다**(T92가 저작). 즉 새 게이트를 그냥 얹으면 기존 fixture와 서로를 부정한다. 이걸 등재 시점에 못 잡으면 구현자가 착수해서야 발견하고, 최악은 **T92가 우회 6종을 재현해 쌓은 역검증 자산을 조용히 지우는 것**이다. 같은 이유로 신고 발화가 프롬프트 파일에 **그대로 저작돼 있는지**도 본다 — 이번 건은 `institutionalImpersonation.prompt.ts:33`(personaPrompt)과 `:61`(weakenedTactics) **두 자리 모두**에 있었고, 5개 시나리오에 복제돼 있었다(모델 창작이 아니라 지시가 요구한 동작).

**⚠️ 2026-07-27 확장 — "어느 기존 행에 붙일까"를 정할 때도 같은 대조를 한다.** 라이브 신고 발화 *"네, 박OO님 맞으시죠? 최근에 통장 개설하신 적 있으세요?"* 를 T112(*"패턴이 변형 의문형을 놓친다"*) 행에 붙일 뻔했는데, **패턴 원문과 대조하니 정반대였다** — `scenarios.test.ts:1045`의 대안 중 `맞으시죠`와 `하신 적 (이)? 있`이 **둘 다 매치**하고 `factInquiry`는 `countsPerMatch: true`라 **한 발화가 2건**으로 세어진다 ⇒ **게이트 기준으로는 잡히는 쪽**이라 T112의 A항과 정면으로 어긋난다. 더 파 보니 진짜 사각은 제3의 것이었다: 두 조각이 **서로 다른 파일에 따로 저작**돼 있고(`promptAssembly.ts:83`의 *"○○○님 맞으시죠?"* + `institutionalImpersonation.prompt.ts:38`의 조회 질문) **각각은 인용구 단위로 1건이라 정당하게 통과**하는데, 게이트가 `quotedUtterances` **인용구 단위로만** 세므로 ***"모델이 인용구 2개를 한 턴에 합치는 것"*** 을 구조적으로 못 본다. ⇒ **"어형 구멍"도 "모델 창작"도 아닌 세 번째 부류**였고, 이건 신규 등재 여부가 사용자 확정 사항이라 **행을 만들지 않고 섹션 서두에 판정과 근거만 적었다.**

**⭐ 2026-10-02 — 충돌 fixture가 *결함을 고정*하는지 *사실에 맞는 다른 하위 경우를 고정*하는지 판별하라.** T182(§69.12 R-5): `src/lib/challenge/mapChallengeItems.test.ts:50-63` 이 `reported` → "완료" 를 단언해 정면 충돌로 보였지만 입력이 `resultSharingConsented: true` 였고 공유 동의는 리포트가 있어야만 된다(`functions/src/challenge/userAccess.ts:410-413`) ⇒ *체험·공유 뒤 신고*라는 **사실에 맞는 경우**였다(결함은 공유 미동의 하위 경우뿐). ⇒ 행에는 *"통째로 빼면 깨진다 · 결함 하위 경우만 다루면 무관"* 으로 적고 고칠지는 결정 대상에 둔다. 판별법: fixture의 나머지 필드가 **상류에서 무엇을 함의하는지**(그 값이 참이려면 무엇이 먼저 일어나야 하나) 서버 쓰기 지점을 grep한다. 또 설계가 *"fixture N곳"* 이라 셀 때 **같은 파일의 다른 상태값 fixture**를 빠뜨렸는지 본다(그날 `completed` 6곳만 세고 `reported` 1곳 누락).

**⭐ 2026-10-02 — *아직 없는* 테스트도 fixture다(T184).** 진행 중인 태스크의 설계 절이 **진리표 테스트를 예정**하고(§69.8 W-1T — 14칸) 그 한 칸이 *"범위 밖 · 무변경"* 이라는 이유로 **지금 결함을 기대값으로 고정**할 예정이었다. ⇒ 등재 시 설계 문서의 **예정 테스트 행**(W-·S-·C- ID)도 grep해, 결함 칸을 고정하면 행에 *"해소 시 그 칸을 바꿔야 함 + 근거 주석"* 을 적고, 진행 중 태스크 행은 건드리지 말고 *"그 칸 옆에 결함 후보 주석을 두라"* 는 권고를 오케스트레이터에게 넘긴다.

**How to apply:** 후속 결함 등재 전 3단계 — ① 신고 발화의 특징 문자열을 `functions/src/scenarios` 전체에 grep, ② 히트를 **정본(프롬프트) / 게이트 fixture**로 분류, ③ fixture 히트가 있으면 태스크 행에 *"기존 게이트를 깨지 않고 축을 얹는 방법을 착수 전 보고"* 를 넣고, fixture 수정이 불가피하면 **근거를 테스트 주석에 남길 것**을 완료 조건에 건다. 관련: [[planner-ac-verifiability]], [[user-scope-narrowing-corrections]]

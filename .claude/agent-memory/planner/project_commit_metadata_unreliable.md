**미등재 커밋을 `docs/Tasks.md`에 사후 등재할 때, 지시문이 준 *커밋 제목*과 *PR 번호 순서*를 사실로 옮겨 적지 마라. 둘 다 반증 가능하고, 실제로 둘 다 틀렸다(2026-09-17, §61~§65 8건 등재).**

**Why:** planner에 셸이 없으면 커밋 객체를 못 읽어 제목·번호가 **유일한 입력**처럼 보인다. 그런데 이 저장소의 architect 절들은 **자기 편집 범위를 닫아 서술**하므로 그것이 곧 **독립 반증 수단**이다.

**반증 2종 (그날 실제로 걸린 것)**

| 무엇을 의심하나 | 어디로 반증하나 | 그날 결과 |
|---|---|---|
| **커밋 제목이 내용을 말하는가** | 그 절의 **"이 패스의 편집 범위(⛔ 정본)"** 블록 — `OQ 신설 N건` · `게이트 N건` · `편집 파일 N개`를 명시한다 | `ce3ddc3`(PR #238)의 제목이 *"docs(§63): … **OQ-A75/A76 신설**"* 인데 **§63.7은 "OQ 신설 0건"** 이었다 — 제목이 **바로 앞 커밋(§62)의 부제를 복사**한 것이다. 제목만 믿었으면 §63을 OQ 신설 커밋으로 등재할 뻔했다 |
| **PR 번호 = 병합 순서인가** | 각 절 서두의 **`base`(= `.git/refs/heads/main` 판독값)** 를 이어 붙이면 **병합 순서가 확정된다** | **PR #237이 PR #236보다 먼저 병합**됐다(§62의 base `659f72a` → §63/§64의 base `716b920`). ⛔ **PR 번호는 생성 시각이지 병합 시각이 아니다** |

**How to apply:**
1. 등재 전, 각 커밋의 **정본 절 "편집 범위" 블록을 먼저 읽어** 제목의 주장(신설·수정·집행)과 대조한다. 어긋나면 **행 본문에 그 불일치를 명시**하고 확인법(`git show <hash> --stat` · `git log -1 --format=%B`)을 함께 적는다.
2. 병합 순서는 **절들의 `base` 체인**으로 세우고, 지시문의 열거 순서와 일치하는지 확인한 뒤 *"PR 번호를 시간순으로 읽지 말 것"* 을 섹션 서두에 박는다.
3. 그래도 **제목·해시·PR 번호·배포 완료 여부는 "지시문 인용값"으로 표기**하고, **산출물 심볼 grep만을 planner 실측값**으로 적는다(2단 확인).
4. ⭐ **설계가 요구한 커밋 분할이 지켜졌는지도 같은 방식으로 의심한다** — §61.13이 *"커밋 2개 · 순서 고정"* 을 요구했는데 PR 제목이 두 변경을 한 줄에 적으면, **분할 요구의 *이유*(그날은 "섞으면 P-E 변화의 귀속이 갈리지 않는다")가 무효화됐는지**를 행에 적어 둔다.

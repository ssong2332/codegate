**오케스트레이터가 라이브 결과를 주며 `done` 집행을 지시해도 증거 목록을 세 곳에 대조한다**: ① 그 행의 완료 증거 문면 ② 설계 절차가 **번호 범위로 통째로 인용한 하위 단계**(2026-10-02: §68.10 S-G가 "§67.9 S-1~S-4"를 인용 → S-3 `createRealtimeCall`이 보고에서 빠져 있었다) ③ AC의 **조건부 항목**(AC-085 (c) "되감기(속은 순간이 있을 때)").

**판정표(T177에서 쓴 J1~J3)**: J1 전 항목 출력 + 조건부 항목이 채널마다 *실행됨* 또는 *해당 없음 확인* → done / J2 User가 "미측정인 채로 수용한다" 명시 → done(원문과 함께) / J3 그 밖(조건부 항목의 **해당 여부 미확인** 포함) → review(라이브 잔여).

**Why:** 2026-10-02 T177은 1차에 `done`으로 적었다가 같은 날 되돌렸다 — 음성 세션에 속은 순간이 있었는지 User가 "기억이 안 남 / 확인 못 함"이라 답해, 익명 되감기(`judgeRewindAnswer`)가 두 채널 모두 라이브 미관측으로 드러났다. 1차 때 이미 "해당 여부가 인용에 없다"를 적고 확인을 요청했지만 done을 먼저 박았다 — **해당 여부 미확인은 "해당 없음"이 아니다.** 그 상태로 done이면 남은 확인이 조용히 사라진다(`review(라이브 검증 대기)` 관례와 같은 이유).

**How to apply:**
1. 조건부 항목은 채널별로 *실행됨 / 해당 없음 확인 / 미확인* 3값으로 적고, 미확인이 하나라도 있으면 done을 박지 않는다 — 확인 요청만 하고 done을 먼저 쓰지 말 것.
2. 승격 조건에는 **그 경로를 실제로 태우는 절차**를 적는다. 사후 조회(예: 리포트의 속은 순간 수)는 문면 판정에는 쓰여도 라이브 관측을 만들지 않으므로 승격 조건으로 쓰지 않는다.
3. 의존 행(T176 ← T177 출력)은 승격 조건이 "상대 행의 출력 존재"인지 "상대 행 done"인지 **문면대로** 판정하고, 상대 행 잔여 확인이 실패하면 재개한다는 조건을 적는다.
4. 관찰된 응답 문구는 소스와 대조해 **어느 검사가 거절했는지** 확정한다 — 같은 403이라도 "본인 세션이 아닙니다"(소유권 `functions/src/roleplay/index.ts:79`)와 게이트 문구(`functions/src/shared/anonymousGate.ts:23`)는 증명하는 AC 조항이 다르다.
5. 1차 처리를 같은 날 되돌릴 때는 미커밋 본인 문면이라도 *"같은 날 1차 처리에서 done으로 적었다가 되돌렸다"* 를 남긴다 — 오케스트레이터는 1차 보고를 이미 읽었다.

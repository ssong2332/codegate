검증·게이트 도구의 한계를 보고할 때 **"못 잡는다"(안전한 방향 실패)와 "틀리게 잡는다"(거짓 OK)를
같은 목록에 나란히 적지 마라.** 후자는 발견 즉시 닫아야 하는 결함이고, 고지만 하고 넘기면 안 된다.

**Why:** T115에서 한계 5가지(검사 미실행·기록 없음·스냅숏·플랫폼·포트)는 전부 `UNKNOWN`/무효로
떨어지는 안전한 실패였는데, 6번째만 **`FRESH`라고 답하는데 실제로는 낡은 코드가 돌고 있는** 경로였다.
나는 "범위 확대 금지" 지시를 지키려고 증거까지 잡아 놓고 **고지만 하고 넘겼다.** 오케스트레이터가
되돌렸다 — *"reviewer가 승인 근거로 든 것이 '애매하면 UNKNOWN, 절대 거짓 FRESH 아님'이었다.
그 전제가 무너지면 누군가 FRESH를 믿고 낡은 코드로 측정한다."* 맞는 지적이었다.

**How to apply:**
1. 한계를 적을 때 **"이 실패는 어느 방향인가"를 먼저 분류**하라. 안전한 방향이면 고지, 거짓 OK 방향이면
   **범위 밖이라도 멈추고 그 자리에서 판단을 요청하라**(고지 목록에 섞어 넣지 말고 별도로 올려라).
2. 닫는 안이 여러 개면 **정밀도보다 "테스트 가능한 층에서 닫히는가"** 로 골라라. T115에서는 OS 조회로
   정확히 판정하는 안 대신, 이미 가진 데이터만 써서 순수 함수 층에서 닫히는 안(보수적 과탐 허용)을
   골랐고 그게 채택됐다. 더 정밀한 안은 **미채택 근거와 함께 주석에 남겨** 다음 사람이 갈 수 있게 한다.
3. 보수적으로 바꾸면 **기존 역검증 기대값이 바뀔 수 있다**(T115 샘플 5: `FRESH`→`UNKNOWN`).
   기대값을 바꾼 이유를 **테스트 주석에** 적어라 — 안 적으면 다음 사람이 회귀로 오해하고 되돌린다.
4. 새 경고를 추가하면 **노이즈 빈도를 실측해서 함께 보고**하라. 상시로 뜨는 경고는 꺼지고,
   꺼진 게이트는 없는 게이트다. "이 조건이 참이 되는 실제 흐름"을 몇 개 돌려 수치로 내라.

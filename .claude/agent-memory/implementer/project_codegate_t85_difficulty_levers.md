T85(난이도 4레버, 브랜치 `feat/T85-difficulty-levers`, 2026-07-26)에서 다음 회차에 재사용할 판단.

**1. 설계 문서의 숫자가 그 사이 병합된 브랜치보다 낡을 수 있다 — 설계가 스스로 예고했는지부터 본다.**
지시와 §17.5는 L3 깊이 분포를 **13종 기준 5/4/4**로 못박았는데, 착수 시점 main은 이미 T95 병합으로 **14종**이었다. 임의 판단으로 보이지만 아니었다 — §17.10 계약 **14항**이 *"T95가 +1종 하면 표도 1행 늘고, 그 행은 hasVerifyIntercept=true일 것이므로 procedural이어야 한다"* 로 미리 규율해 뒀다. 그래서 6/4/4로 구현하고 테스트 주석·완료 보고 양쪽에 "설계값 5/4/4 + 예고된 증분"임을 적었다.
**How to apply:** 설계와 코드가 숫자에서 어긋나면 (a) 설계 안에 그 증분을 예고한 조항이 있는지 먼저 찾고 (b) 있으면 그대로 따르되 **어긋난 사실 자체를 보고에 쓴다**. 없으면 구현하지 말고 보고한다.

**2. 호출부 3곳 중 관측 가능한 것이 1곳뿐일 때 — 행동 단언 + 소스 게이트를 섞는다.**
`buildSystemPrompt` 호출부는 sendMessage(Firestore 콜러블)·openingLine(조립 결과를 밖으로 안 내보냄, Mock LlmClient가 입력을 기록하지 않음)·geminiProvider(토큰 발급 본문에 systemInstruction이 그대로 실림) 셋인데, 조립 결과를 관측할 수 있는 것은 마지막 하나뿐이다. 그래서 geminiProvider엔 **행동 단언**을, 나머지 둘엔 소스 파일을 읽어 `l3Procedural: isL3Procedural(` 리터럴 + import 경로를 검사하는 **소스 게이트**를 뒀다(선례: `scenarios.test.ts`의 AC-073 신호 리터럴 검사).
**Why:** 옵션 부재의 기본값이 "축소"라 빠뜨려도 **에러가 나지 않는다**(§17.11 G63). 관측 못 하는 경로를 그냥 비워 두면 그 경로만 조용히 다르게 동작한다.
**How to apply:** 소스 게이트는 한계를 테스트 주석에 함께 적는다("넘기긴 하는데 값이 틀린 경우"는 못 잡는다 → 판정 함수를 한 곳으로 묶어 구조로 막는다). 검사 대상에 **함수 호출 형태까지** 넣으면 호출부가 자체 규칙을 재발명하는 것도 함께 막힌다.

**3. 축 커버리지 공백을 하나 채우면 최소 4개 단언이 동시에 깨진다(설계된 동작).**
`loan-refinance-scam`에 D4를 태깅하자 `axisCoverage.test.ts`에서 ① 0건 집합 하드코딩 ② 양방향 `DECLARED_COVERAGE_GAPS` deepEqual ③(신설한) 채움 확인 ④ 필수 4값 확인이 함께 움직였다. `DECLARED_COVERAGE_GAPS`의 해당 행 **삭제가 해소 기록**이라는 규약도 파일 주석에 있다.
**How to apply:** 공백 채우기 태스크를 받으면 `axisCoverage.ts` 주석 규약 → `axisCoverage.test.ts` 하드코딩 숫자 → 리포트 스크립트(`npm run report:axis-coverage`) 순으로 훑고, 리포트 출력 한 줄(`| D4_... | 1 | loan-refinance-scam |`)을 증거로 인용한다.

**4. 프롬프트 문구를 "지우는" 것이 태스크 산출물일 때가 있다.**
G61은 기능 추가가 아니라 기존 고급 문구 `"요구에 더 빨리 도달한다"` **삭제**가 본체였다(남겨 두면 새 레버가 발동하지 않는다). 삭제를 회귀로 오인당하지 않게 **"이 문구가 없어야 한다"는 부정형 테스트**를 함께 넣었다.
**How to apply:** 프롬프트 층에서 "새 지시가 기존 지시와 모순되지 않는가"를 착수 전에 grep으로 확인하고, 모순 문구는 삭제 + 부정형 테스트로 고정한다.
